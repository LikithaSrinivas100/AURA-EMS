# AURA-EMS Dataset and ML Pipeline

## Dataset contract

Place `alliance_campus_energy_master.csv` at `data/alliance_campus_energy_master.csv`. The first CSV column must contain parseable timestamps. Rows must represent a continuous 15-minute time series. The target is `Total_Campus_Demand_kW`; required input columns are `Hour`, `DayOfWeek`, `Month`, `Temperature_C`, `Is_Weekend`, `Is_Vacation`, and `Is_Exam_Cycle`.

The loader parses and sorts the timestamps, rejects duplicates and non-numeric or missing target values, reports negative target rows and missing values, and rejects negative demand or a non-continuous 15-minute index. This strict frequency check is important: row-based shifts only mean one hour and 24 hours when timestamps are regular.

## Run from the project root

```powershell
python -m pip install -r requirements-ml.txt
python -m ml.feature_engineering
python -m ml.train
python -m ml.evaluate
```

For a dataset stored elsewhere, pass `--input path\to\alliance_campus_energy_master.csv` to feature engineering. The scripts write the chronological split under `outputs/`, experiment models under `models/`, final metrics and dashboard feed under `outputs/`, plots under `reports/`, and the generated evaluation report to `reports/ml_evaluation.md`.

## Leakage and evaluation

Rows stay in timestamp order; the first 80% of usable rows train the models and the last 20% form the held-out future test. Demand lags use shifts of 4, 8, and 96 rows. The 4-hour rolling mean and standard deviation use the prior 16 rows after shifting demand by one row, so the current target is excluded. Rows without a complete lag/rolling window or required feature are removed before the split.

The benchmark predicts the demand observed 24 hours earlier. XGBoost and LightGBM use the same training rows and feature list. The production artifact is selected by lowest held-out RMSE across the baseline and both tree models. MAPE excludes zero actual values, where percentage error is undefined; the excluded count is recorded in `metrics.json`.

## Integration contract

Feature order is fixed and written into `outputs/metrics.json`:

`Hour`, `DayOfWeek`, `Month`, `Temperature_C`, `Is_Weekend`, `Is_Vacation`, `Is_Exam_Cycle`, `Load_Lag_1hr`, `Load_Lag_2hr`, `Load_Lag_24hr`, `Load_Rolling_Mean_4hr`, `Load_Rolling_Std_4hr`.

The dashboard feed is indexed by `Timestamp` and contains `Actual_Demand_kW`, `XGB_Predicted_Demand_kW`, `LGB_Predicted_Demand_kW`, and `Best_Predicted_Demand_kW`. Backend integration should consume this feed and metrics; the frontend should not load the pickle.
